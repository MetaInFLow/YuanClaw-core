## Description 设计

Description 是 Skill 能否被正确触发的关键。它是 Claude 判断"要不要调用这个 Skill"的唯一依据。

### 写法要素

一个强 description 需要包含三个层次：

1. **核心能力**：用具体动词描述 Skill 做什么（提取、生成、拆解、转换……）
2. **触发场景**：列出 2-3 个典型使用场景
3. **边界暗示**：暗示不适用的场景（可选，但有助减少误触发）

### 弱 vs 强 对比

| 弱 description | 问题 | 强 description |
|---------------|------|---------------|
| `帮助处理文档` | 太泛，几乎什么都能匹配 | `从 PDF 中提取表格并转为 CSV，用于数据分析工作流` |
| `文档处理技能` | 缺少动词、场景、边界 | `综合 PDF 工具：提取文本和表格、创建新 PDF、合并拆分文档、处理表单。用于文档批处理和自动化工作流。不用于简单 PDF 查看或基础格式转换` |
| `项目管理助手` | 模糊，不知道具体做什么 | `将项目方案自动拆解为功能清单和 SOW；适用于售前报价、需求确认、开发依据；当用户提到"拆解方案"、"功能清单"、"SOW"时触发` |

### 长度指南

- **目标**：100-150 字符（中文）
- **底线**：至少包含一个具体动词 + 一个使用场景
- **上限**：不超过 200 字符，超长反而降低触发精度

### "适度推销"策略

Claude 当前的倾向是"少触发"——宁可不调用 Skill，也不愿误调用。因此 description 可以稍微主动一些：

- 列出多种触发短语变体
- 包含同义词和相关场景
- 明确说"即使用户只是提到 XX 也应触发"（谨慎使用）

但要保持平衡——过度推销会导致不相关场景也触发。

## 触发机制原理

理解 Claude 如何决定调用 Skill，有助于设计更好的触发策略。

### 语义匹配，非关键词

Claude 评估用户请求与 Skill description 的**语义相关性**，不是关键词匹配。这意味着：

- 用户不必说出 description 中的原话就能触发
- "帮我把方案拆开看看" 可以匹配 "将项目方案拆解为功能清单"
- 但过于泛化的 description 会导致语义重叠，产生误触发

### 多 Skill 并行

多个 Skill 可以同时被激活，前提是它们处理请求的不同方面。设计 Skill 时考虑：

- 你的 Skill 和其他 Skill 之间是否有语义重叠
- 如果有，description 中的边界暗示能否帮助区分

### 简单任务不触发

Claude 对于自身就能轻松完成的简单任务（如"读这个文件"、"解释这段代码"），不太会调用 Skill，即使 description 匹配。Skill 对**复杂、多步骤、需要专业知识**的任务最有效。

## 渐进式加载

Skill 有三层加载机制，合理利用可以控制上下文窗口的消耗：

| 层级 | 内容 | 加载时机 | 体量建议 |
|------|------|---------|---------|
| 元数据 | name + description | 始终在上下文中 | ~100 词 |
| SKILL.md 正文 | 核心流程和步骤 | Skill 被触发时 | <500 行 |
| Reference 文件 | 详细模板、规范、示例 | 按需读取 | 无限制（单个 <300 行为佳） |

### "菜单"模式

当 Skill 覆盖多个领域/变体时，SKILL.md 应像菜单一样描述有哪些选项，然后用链接指向各自的 reference 文件。Claude 只读取与当前任务相关的那个。

```
skill-name/
├── SKILL.md          # 描述选项 + 路由逻辑
└── references/
    ├── variant-a.md  # 场景 A 的详细指南
    ├── variant-b.md  # 场景 B 的详细指南
    └── variant-c.md  # 场景 C 的详细指南
```

### 体量红线

- SKILL.md 超过 500 行 → 必须拆分
- Reference 超过 300 行 → 加目录，考虑拆分
- 嵌套引用只允许一层（Skill → Reference，不允许 Reference → Reference）

## 成功标准设计

把成功标准写进 Skill，让 Claude 能够自检输出质量。

### 什么是好的成功标准

- **具体可验证**：`每个需求编号格式为 FR-XXX-001` 比 `编号规范` 好
- **有底线有上限**：区分"必须满足"和"最好满足"
- **可自动检查**：Claude 能通过规则判断是否达标，不需要人类感性评估

### 在 Skill 中的位置

成功标准通常放在"质量检查清单"章节，用 checkbox 格式：

```markdown
## 质量检查清单
- [ ] 每个功能描述包含动作+对象+能力
- [ ] 需求编号全局唯一，格式 FR-[缩写]-[三位序号]
- [ ] P0 优先级不超过总需求的 30%
```

## 测试与验证

### 三类场景覆盖

设计测试用例时，确保覆盖三个维度：

**1. 正常操作测试**

用典型请求验证 Skill 的核心功能是否正常。选择 2-3 个代表性场景，覆盖 Skill 的主要能力。

**2. 边缘情况测试**

测试非理想输入下的表现：
- 输入信息不完整
- 格式不符预期
- 用户表达模糊
- Skill 应优雅降级（提问补齐、给出部分结果+说明）而不是崩溃或硬编

**3. 不应触发测试**

最有价值的负面测试不是"明显无关"的请求（那太简单），而是**近似但不应触发**的请求。例如：

- Skill 做"方案拆解" → 测试"合同审查"（有语义重叠但不同任务）
- Skill 做"功能清单" → 测试"项目排期"（同一项目流程但不同阶段）

### 触发测试 vs 功能测试

| 维度 | 触发测试 | 功能测试 |
|------|---------|---------|
| 测什么 | Skill 在正确时机被调用/不被调用 | Skill 调用后输出质量是否达标 |
| 怎么测 | 用不同措辞的请求验证 | 用标准输入对比输出和成功标准 |
| 关注点 | Description 的覆盖面和精度 | 流程、模板、自检规则的有效性 |

## 常见反模式

| 反模式 | 问题 | 改进 |
|--------|------|------|
| "全能 Skill" | description 太泛，什么都能匹配 | 聚焦到一个具体任务 |
| "隐形 Skill" | description 太窄或太抽象，永远触发不了 | 加入多种触发短语和场景 |
| "胖 Skill" | 所有细节都堆在 SKILL.md | 拆到 references/，正文只留核心流程 |
| "无标准 Skill" | 没有成功标准，输出质量全凭运气 | 加入质量检查清单和自检规则 |
| "孤岛 Skill" | 不考虑和其他 Skill 的关系 | 在 description 中暗示边界 |
| "一次性 Skill" | 解决的是只做一次的任务 | 确认任务重复频率（5+次），否则别做 Skill |
