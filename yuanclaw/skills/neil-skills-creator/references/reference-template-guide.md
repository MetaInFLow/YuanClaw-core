## 文档目的

Reference文档用于定义"长什么样"——包括：
- 输出模板
- 字段规范
- 写法标准
- ✅❌对比示例

**与Skill的分工**：
- Skill：定义"怎么做"（流程、步骤、判断规则）
- Reference：定义"长什么样"（模板、规范、示例）

---

## 结构规范

### 必需章节

#### 1. 目录（超过100行必需）
列出主要章节和锚点链接，便于快速导航。

**示例**：
```markdown
## 目录
- [表格结构](#表格结构)
- [字段说明](#字段说明)
- [写法规范](#写法规范)
- [示例](#示例)
```

#### 2. 概览
一句话定义文档的适用范围和用途。

**示例**：
```markdown
## 概览
功能需求清单模板规范，用于标准化项目需求管理和开发依据。
```

#### 3. 核心内容

**表格结构**（如果输出是表格）：
- 列出所有字段
- 定义格式要求
- 说明填写规则

**示例**：
```markdown
## 表格结构

| 字段 | 格式 | 说明 |
|------|------|------|
| 分类 | `模块X：模块名称` | 按业务域划分的大类 |
| 需求编号 | `FR-[缩写]-[三位序号]` | 全局唯一标识 |
| 功能模块 | 3-8字名词短语 | 功能点名称 |
| 功能描述 | 一句话 | 做什么 + 支持什么 |
| 优先级 | P0/P1/P2 | 重要程度 |
```

**字段说明**：
- 每个字段的详细解释
- 填写约束和注意事项
- 示例

**示例**：
```markdown
## 字段说明

### 需求编号
**格式**：`FR-[缩写]-[三位序号]`

**说明**：
- FR：Functional Requirement（功能需求）
- 缩写：项目或模块的英文缩写（如SYS-系统模块）
- 序号：001-999，全局唯一

**示例**：
- FR-SYS-001（系统模块第1个需求）
- FR-USER-023（用户模块第23个需求）
```

#### 4. 写法规范
- 定义标准句式或格式
- ✅ 好的写法示例
- ❌ 差的写法示例

**示例**：
```markdown
## 写法规范

### 功能描述句式
**标准句式**：[动作] + [对象] + [能力/特性]

**✅ 好的写法**：
- 实现规则的增删改查、启用/禁用、排序、搜索功能，支持按策略类型筛选
- 支持用户登录、登出、密码重置，支持邮箱和手机号登录

**❌ 差的写法**：
- 规则管理（太笼统）
- 做一个好用的界面（无法验收）
- 支持很多功能（不具体）
```

#### 5. 完整示例
- 提供可复制的空白模板
- 提供2-3个完整的填充示例
- 示例要真实、具体

**示例**：
```markdown
## 空白模板

| 分类 | 需求编号 | 功能模块 | 功能描述 | 优先级 |
|------|----------|----------|----------|--------|
| 模块X：XXX | FR-XXX-001 | | | |

## 完整示例

| 分类 | 需求编号 | 功能模块 | 功能描述 | 优先级 |
|------|----------|----------|----------|--------|
| 模块1：用户管理 | FR-SYS-001 | 用户登录 | 支持用户使用邮箱和手机号登录，支持密码验证和验证码登录 | P0 |
| 模块1：用户管理 | FR-SYS-002 | 用户注册 | 支持新用户注册，需要邮箱验证 | P0 |
| 模块2：规则管理 | FR-SYS-003 | 规则增删改 | 实现规则的增删改查、启用/禁用、排序、搜索功能 | P1 |
```

#### 6. 约束与注意事项
- 填写的约束条件
- 常见错误和避免方法
- 特殊情况处理

## 编写原则

### 清晰性
- 每个字段、规范都有明确的说明
- 示例要具体、真实
- ✅❌对比要有说服力

### 完整性
- 包含所有必要的信息（格式、约束、示例）
- 不能让使用者猜测或填补

### 可操作性
- 提供可直接复制的空白模板
- 示例可以复制后直接修改使用

### 一致性
- 格式、命名、术语要保持一致
- 与Skill中的描述保持一致

---

## 格式规范

### 表格格式
- 使用Markdown表格
- 列名要清晰（字段、格式、说明）
- 示例要真实

### 代码格式
- 使用行内代码标记格式和示例（如 `FR-SYS-001`）
- 使用代码块展示完整模板

### 标题层级
- H2（##）用于主要章节
- H3（###）用于子章节
- H4（####）用于更细分的内容

## 字段说明

### 分类
**格式**：`模块X：模块名称`

**说明**：
- 按业务域划分的大类
- 模块X：数字序号（1、2、3...）
- 模块名称：中文名称

**示例**：
- 模块1：用户管理
- 模块2：规则管理
- 模块3：报表分析

### 需求编号
**格式**：`FR-[缩写]-[三位序号]`

**说明**：
- FR：Functional Requirement（功能需求）
- 缩写：项目或模块的英文缩写（如SYS-系统模块）
- 序号：001-999，全局唯一

**示例**：
- FR-SYS-001（系统模块第1个需求）
- FR-USER-023（用户模块第23个需求）

### 功能模块
**格式**：3-8字名词短语

**说明**：
- 功能点的名称
- 简洁明确，易于理解

**示例**：
- 用户登录
- 规则管理
- 报表导出

### 功能描述
**格式**：一句话描述

**说明**：
- 说明"做什么" + "支持什么"
- 语言要具体、可验收

### 优先级
**格式**：P0/P1/P2

**说明**：
- P0：核心功能，必须有
- P1：重要功能，强烈建议有
- P2：增强功能，可以后做

## 写法规范

### 功能描述句式
**标准句式**：[动作] + [对象] + [能力/特性]

**✅ 好的写法**：
- 实现规则的增删改查、启用/禁用、排序、搜索功能，支持按策略类型筛选
- 支持用户登录、登出、密码重置，支持邮箱和手机号登录
- 支持按日期、类型、状态筛选报表，支持导出Excel和PDF

**❌ 差的写法**：
- 规则管理（太笼统）
- 做一个好用的界面（无法验收）
- 支持很多功能（不具体）
- 实现用户相关功能（范围不明）

## 约束与注意事项

1. **需求编号唯一性**：同一项目中需求编号不能重复
2. **功能描述可验收**：描述要具体、明确，能够被测试和验收
3. **优先级合理性**：P0功能不应超过总功能数的30%
4. **模块划分清晰**：同一模块内的功能应相关性强
5. **避免重复**：相似功能要合并，不要拆成多个需求

---

## 常见错误

| 错误 | 正确做法 |
|------|---------|
| 功能描述太笼统："规则管理" | 具体描述："实现规则的增删改查、启用/禁用" |
| 优先级混乱 | 明确P0/P1/P2的定义，合理分配 |
| 需求编号不规范 | 严格按照格式编写 |
| 模块划分不清 | 按业务域划分，相关性强的放一起 |
