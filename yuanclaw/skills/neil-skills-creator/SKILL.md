# Neil Skills Creator

## 定位

本技能分两个阶段工作：

- **阶段一（想清楚）**：通过方法论引导用户完成需求分析、问题定义、输出物定义、流程设计、模板打磨
- **阶段二（做出来）**：调用 `skill-creator` 完成 Skill 编写、测试评估、迭代优化、描述优化、打包发布

## Skill 设计核心思考

在整个设计过程中，以下原则应贯穿始终。这些原则来自 Skill 触发机制和实战经验，理解它们能让你设计出真正好用的 Skill。

### 原则一：Description 决定生死

Description 是 Skill 能否被正确触发的唯一关键。Claude 通过语义理解（不是关键词匹配）判断是否调用 Skill，因此：

- **写能力 + 场景 + 边界**：不只说"能做什么"，还要说"什么时候用"和"什么时候不用"
- **用具体动词**：`提取表格`、`生成报告`、`拆解方案` 比 `处理文档` 有效得多
- **适度"推销"**：Claude 倾向于"少触发"，description 要稍微主动一些，列出多种触发场景

> 弱 description：`帮助处理文档和数据`
>
> 强 description：`将项目方案自动拆解为功能清单和SOW；适用于售前报价、需求确认、开发依据等场景；当用户提到"拆解方案"、"功能清单"、"SOW"、"报价"时触发`

### 原则二：从真实重复中来

好 Skill 解决的是你已经做过 5 次、还会再做 10 次的任务。如果一个任务只做一次，写成 Skill 反而是浪费。在零步需求分析时，问用户："这件事你做过几次？以后还会做吗？"

### 原则三：把成功标准写进 Skill

告诉 Claude "好的输出长什么样"。如果生成的是报告，指定必需章节、格式标准、质量阈值。把这些标准写在 Skill 中，Claude 就能自检。

### 原则四：渐进式加载

- SKILL.md 保持在 500 行以内，只放核心流程
- 详细模板、规范、示例放 references/
- Claude 只在需要时才读取 reference 文件，不会每次都加载全部内容
- 如果 Skill 覆盖多个领域，用"菜单"模式：SKILL.md 描述有哪些选项，reference 文件各管各的

### 原则五：测试要覆盖三类场景

| 场景类型 | 测什么 | 示例 |
|---------|--------|------|
| 正常操作 | 典型请求能否正确处理 | "帮我把这个方案拆成功能清单" |
| 边缘情况 | 输入不完整/异常时的表现 | 用户只给了半页方案 |
| 不应触发 | 相似但不属于本 Skill 的请求 | "帮我审查这份合同"（不是拆解方案） |

详细设计原则见 [references/skill-design-principles.md](references/skill-design-principles.md)。

## 阶段一：方法论引导

### 零步：需求分析与定位

当用户需求模糊时执行（如"我想要一个Skill"、"帮我解决问题"）。需求明确则跳过。

#### 1. 收集需求信息

逐步深入了解：

| 问题类型 | 具体问题 | 获取信息 |
|---------|---------|---------|
| 基础信息 | 你希望解决什么问题？能否描述一下具体场景？ | 问题背景、使用场景 |
| 现状痛点 | 现在是怎么做的？遇到了什么困难？ | 痛点、改进点 |
| 期望目标 | 你希望达到什么效果？理想的状态是怎样的？ | 目标、预期 |
| 使用场景 | 这个Skill会在什么情况下被使用？谁会使用它？ | 触发场景、使用者 |

提问技巧：从开放性问题开始，逐步聚焦，避免一次问太多。

#### 2. 需求定位分析

| 维度 | 分析问题 | 判断依据 |
|------|---------|---------|
| 任务类型 | 重复性还是创造性？ | 重复性→需流程；创造性→需模板 |
| 复杂度 | 简单还是复杂？ | 简单→一步到位；复杂→分步确认 |
| 输出物 | 需要输出什么？ | 表格→需模板规范；文档→需结构 |
| 技术性 | 是否涉及文件处理或API？ | 是→需脚本；否→智能体处理 |
| 确认需求 | 输出是否重要？ | 重要→分步确认；不重要→一步到位 |

输出格式：
```
[需求分析报告]
1. 问题定位：[一句话概括]
2. 适用场景：[2-3个典型场景]
3. 关键能力：[核心能力列表]
4. 技术要求：是否需要脚本/模板/中间层/分步确认
5. 推荐方案：[构建策略]
```

#### 3. 与用户确认

输出分析报告后，请求用户确认。确认无误进入第一步，有调整则修改后再确认。

---

### 第一步：明确要解决的问题

| 问题 | 说明 |
|------|------|
| 要解决什么问题 | 具体的业务痛点 |
| 现状是怎样的 | 现在怎么做？痛点在哪？ |
| 期望变成怎样 | 用了Skill之后的理想状态 |

产出：**问题定义文档**

---

### 第二步：定义关键输出物

| 问题 | 说明 |
|------|------|
| 输出什么 | 表格？文档？代码？ |
| 给谁用 | 使用者是谁？ |
| 用来干嘛 | 业务用途 |

产出：**输出物定义**

---

### 第三步：设计工作流程

1. 明确输入是什么
2. 明确输出是什么（第二步已定义）
3. 设计中间步骤
4. 考虑异常情况（信息不足时先提问，不硬拆）
5. 设计确认点（重要输出建议分步确认）

**何时需要中间层**：
- 从输入到输出的思考过程模糊
- 输出物很重要，不能出错
- 希望用户看到推导过程

详细方法论见 [references/agent-skill-methodology.md](references/agent-skill-methodology.md) 的"Tips：何时需要中间层"章节。

产出：**工作流程文档**

注意：流程和模板是交替打磨的，不必等流程完全定稿再做模板。

---

### 第四步：打磨输出模板

为每个输出物定义详细模板规范：

1. 找一个实际做过的好案例
2. 抽出结构（字段、格式）
3. 定义字段填写规范
4. 对比好差写法（✅❌）
5. 给出空白模板和完整示例

模板编写参考 [references/reference-template-guide.md](references/reference-template-guide.md)。

产出：**Reference 文档（模板规范）**

---

## 桥接：生成需求规格书

完成前四步后，你已经有了清晰的产出物（问题定义、输出物定义、工作流程、模板规范）。在交接给 skill-creator 之前，需要将这些产出整合为一份正式的**需求规格书**。

### 为什么要生成规格书

规格书不是重复劳动，而是：
- **质量关卡**：强制自检阶段一的产出是否完整、一致
- **触发设计**：阶段一专注于"做什么"，规格书补充"何时触发"和"何时不触发"（核心思考原则一）
- **成功标准**：将隐含的质量预期显性化，写进规格书（核心思考原则三）
- **测试策略**：提前规划三类测试场景（核心思考原则五）
- **交接契约**：skill-creator 基于规格书工作，产出更精准

### 操作步骤

1. **使用模板**：基于 [assets/skill-spec-template.md](assets/skill-spec-template.md) 填写规格书
2. **填写内容**：
   - 第 1-2 节：从第一步"问题定义"提取
   - 第 3 节（触发设计）：结合核心思考原则，设计 description 草稿、触发短语、不应触发场景
   - 第 4-6 节：从第二至四步的产出提取
   - 第 7 节（成功标准）：定义输出质量标准和自检规则
   - 第 9 节（测试策略）：规划正常/边缘/不应触发三类测试用例
   - 第 10 节（文件结构）：规划 Skill 的文件组织和渐进式加载策略
3. **保存规格书**：以 `[skill-name]-spec.md` 命名，保存到 Skill 工作目录
4. **用户确认**：将完整规格书展示给用户，确认后进入阶段二

### 规格书产出格式

```
文件名：[skill-name]-spec.md
内容：基于 assets/skill-spec-template.md 填写的完整规格书
状态：用户确认后定稿
```

### 质量检查

- [ ] 所有 10 个章节均已填写（无空白占位）
- [ ] Description 草稿符合"能力+场景+边界"三要素
- [ ] 至少有 3 个触发短语和 2 个不应触发场景
- [ ] 成功标准具体可验证（不是"质量好"这种模糊描述）
- [ ] 测试策略覆盖正常/边缘/不应触发三类
- [ ] 文件结构规划考虑了渐进式加载

## 阶段二：调用 skill-creator

规格书确认后，调用 `skill-creator` 来完成技术实现。

### 第五步：基于规格书整合为 Skill

调用 `/skill-creator`，将需求规格书作为核心上下文传递。告诉 skill-creator：

```
我已经完成了需求梳理和规格书编写，以下是交接材料：

1. 需求规格书：[指向 skill-name-spec.md 路径]
2. 模板规范（Reference 文档）：[指向 references/ 路径]

规格书中已包含：
- 问题定义、输出物定义、工作流程
- Description 草稿和触发设计
- 成功标准和自检规则
- 测试策略（正常/边缘/不应触发三类用例）
- 文件结构规划

请基于规格书：
- 编写 SKILL.md（采用规格书中的 description 草稿作为起点）
- 使用规格书第 9 节的测试用例运行评估
- 生成 eval viewer 供我审查
```

skill-creator 会接管以下工作：
- 编写 SKILL.md（遵循其 Skill Writing Guide，以规格书为蓝图）
- 基于规格书的测试策略创建测试用例
- 并行运行 with-skill 和 baseline 测试
- 起草量化评估断言（参考规格书的成功标准）
- 生成 eval viewer 供用户审查结果

### 第六步：验证与迭代

继续在 skill-creator 的迭代循环中工作：

1. 用户通过 eval viewer 审查输出、留下反馈
2. skill-creator 读取反馈，改进 Skill
3. 重新运行测试，生成新一轮 viewer
4. 重复直到满意

迭代完成后，可选操作：
- **描述优化**：skill-creator 的 Description Optimization 流程，优化触发准确率
- **打包发布**：skill-creator 的 Package 功能，生成 .skill 文件

## 注意事项

- **迭代原则**：不是线性走完就结束，流程和模板交替打磨
- **先有后好**：先出初版用起来，不追求一次完美
- **精简原则**：Skill 讲"怎么做"，Reference 讲"长什么样"，不重复
- **需求定位优先**：用户需求模糊时，必须先执行零步
- **规格书是桥梁**：阶段一的产出通过需求规格书整合，规格书越完整，skill-creator 在阶段二的效果越好
- **核心思考贯穿始终**：五条设计原则不只在规格书阶段用，整个设计过程都要时刻对照

## 边界说明

**能做**：
- 引导用户从模糊需求到清晰定义（阶段一）
- 调用 skill-creator 完成技术实现（阶段二）
- 提供方法论指导和模板资源

**不能做**：
- 替代用户思考和决策
- 跳过需求梳理直接创建 Skill
- 脱离 skill-creator 独立完成测试评估和迭代优化
